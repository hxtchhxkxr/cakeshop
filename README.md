# cakeshop — 상품·재고와 관리자 통계 개발

케이크 매장의 상품 탐색부터 주문·결제, 관리자 운영까지 연결한 Spring Boot 기반 팀 프로젝트입니다. 저는 **상품·대시보드·통계**를 담당하며, 처음으로 백엔드 도메인을 직접 구현했습니다.

- **개발 기간:** 2026.07 ~ 2026.08
- **팀 인원:** 6명(본인 포함)
- **개발자:** [hxtchhxkxr](https://github.com/hxtchhxkxr)
- **팀 프로젝트 원본:** [team-sweethan/cakeshop](https://github.com/team-sweethan/cakeshop)
- **주요 기술:** Java 21 · Spring Boot 4.0.2 · Spring MVC · MyBatis · MariaDB · Thymeleaf · HTML/CSS/JavaScript
- **이 문서의 범위:** 팀 프로젝트에서 본인이 담당한 구현, 문제 해결 과정, 배운 점

## 프로젝트에서 얻고 싶었던 것

수업과 학습에서 추상적으로 느꼈던 기술을 직접 사용하며 이해하는 것이 목표였습니다. MyBatis로 작성한 SQL이 실제 데이터를 조회하고, Controller가 전달한 값이 Thymeleaf 화면에 표시되는 과정을 눈으로 확인하고 싶었습니다.

기능의 난도를 높이기보다 **제가 맡은 도메인에서 요청이 들어오고, 업무 규칙을 처리하고, DB와 화면으로 이어지는 전체 흐름을 확실히 이해하는 것**에 집중했습니다. 흐름이 복잡하게 느껴질 때는 흐름도를 그리며 처리 순서와 연동 지점을 정리했습니다.

| 선택 | 이번 프로젝트에서 집중한 학습 |
|---|---|
| MyBatis | SQL과 조회 조건을 직접 작성하고, 데이터 변경이 이루어지는 과정을 이해 |
| Spring MVC · Thymeleaf | 요청 처리, Model 전달, 서버에서 HTML을 만드는 흐름 이해 |
| HTML · CSS · JavaScript | 화면과 서버의 연결을 직접 구현하며 입력과 결과 표시의 흐름 이해 |

JPA와 React는 다음 프로젝트에서 사용할 계획입니다. 이번 프로젝트에서는 SQL과 서버 렌더링의 기본 흐름을 경험하는 데 초점을 맞췄습니다.

## 핵심 경험 1. 재고 변경의 예외 상황과 도메인 책임 분리

### 문제

재고는 수량을 더하고 빼는 연산만으로 끝나지 않았습니다. 구현과 리뷰 과정에서 다음과 같은 상황을 고려하게 됐습니다.

- 여러 주문이 같은 상품의 재고를 동시에 차감하는 경우
- 재고를 확인한 뒤 변경하기 전에 관리자가 상품 설정을 수정하는 경우
- 결제 시 재고를 차감했지만 취소 전 상품 유형이나 판매 상태가 바뀌는 경우
- 같은 결제·취소 요청이 반복되어 중복 차감·복구될 수 있는 경우

특히 **현재 상품 설정만으로는 과거 주문에서 실제로 재고를 차감했는지 알 수 없다**는 점이 중요했습니다.

### 구현과 책임 분리

**조건부 UPDATE와 행 잠금**

재고가 요청 수량 이상일 때만 차감하도록 SQL에 조건을 두고, 변경 행 수가 0이면 실패로 처리했습니다. 이후 재고 상태 판단과 변경 사이의 동시 수정 문제를 다루기 위해 `SELECT ... FOR UPDATE`를 적용했습니다.

재고 변경 작업은 하나의 트랜잭션 안에서 잠금 조회와 변경을 수행합니다. 이는 해당 작업 중의 동시 변경을 제어하는 장치이며, 오래전에 열린 관리자 수정 화면의 값까지 자동으로 검증하는 것은 아닙니다.

**실제 차감 여부를 반환하는 계약**

`decreaseStock(productId, quantity)`가 실제 유한 재고 차감 여부를 반환하도록 했습니다. 주문·결제 쪽은 이 값을 차감 이력으로 보관하고, 취소 시 복구 호출 여부를 판단하도록 협의했습니다.

| 상품 도메인 | 주문·결제 도메인 |
|---|---|
| 재고의 원자적인 차감·복구 연산 제공 | 주문 상태와 차감 이력 관리 |
| 재고 부족과 변경 실패를 명시적으로 전달 | 같은 주문의 중복 차감·복구 방지 |
| 차감 이후 판매 상태나 상품 유형이 바뀐 경우의 복구 처리 | 전체 트랜잭션과 외부 결제 취소·환불 흐름 관리 |

`restoreStock(productId, quantity)`는 주문 식별자를 받지 않으므로, 그 자체로 같은 주문의 중복 취소를 판별할 수 없습니다. 이 구분을 통해 어느 도메인이 무엇을 책임지는지 명확히 했습니다.

### 확인한 결과와 배운 점

재고 부족, 무제한 재고, 판매 중지, 잘못된 수량, 복구 실패 등의 시나리오를 테스트로 다뤘습니다. 예외 상황 중 일부는 코드 리뷰를 통해 발견했고, 피드백을 이해한 뒤 반환값·복구 기준·잠금 방식을 보완했습니다.

이 과정에서 **현재 상태와 과거 작업 이력을 구분해야 하며, 안전한 연동을 위해 중복 처리와 실패 대응의 책임도 합의해야 한다**는 점을 배웠습니다.

## 핵심 경험 2. 통계 조회 구조를 바꾸며 재집계와 실패 복구까지 설계

### 문제와 선택

처음에는 통계 화면을 조회할 때마다 주문·결제 원본을 집계했습니다. 실제 지연을 측정한 것은 아니지만, 데이터가 증가하면 같은 집계를 반복하는 비용이 커질 것으로 예상했습니다.

이에 **일별 집계 결과를 저장하고, 화면에서는 집계 테이블을 조회하는 구조**로 전환했습니다.

| 구성 | 역할 |
|---|---|
| `daily_statistics` | 날짜별 주문·매출 및 활동·금액 지표 저장 |
| `daily_product_statistics` | 날짜별 상품 통계 저장 |
| `statistics_batch_runs` | 집계 실행 상태, 대상 기간, 진행일과 heartbeat 기록 |
| 정기 집계 | 매일 00:10, 서울 시간 기준으로 전날과 변경된 과거 날짜 집계 |
| 기간별 조회 | 집계 결과를 사용하며 오늘·미래 날짜는 제외 |

### 집계 데이터를 유지하기 위한 설계

집계 테이블을 만들자, 원본이 변경되거나 배치가 실패했을 때 저장된 결과를 어떻게 관리할지 결정해야 했습니다.

| 상황 | 대응 |
|---|---|
| 과거 주문·결제 상태 변경 | `updated_at` 기준으로 변경을 탐색하고 해당 과거 날짜 재집계 |
| 운영자가 과거 기간을 다시 계산해야 함 | 기간을 지정하는 수동 `REBUILD` 제공 |
| 초기 과거 데이터 적재 | `BACKFILL` 제공, 중단 시 마지막 완료일 다음 날짜부터 재개 |
| 같은 기간을 다시 집계 | 기존 결과를 교체해 중복 누적 방지 |
| 한 날짜를 저장하다 실패 | 날짜별 독립 트랜잭션으로 롤백해 그 날짜의 기존 결과 보존 |
| 여러 집계가 동시에 실행 | 생성 컬럼과 UNIQUE 제약으로 하나의 `RUNNING` 실행만 허용 |
| 프로세스 중단 후 실행 상태가 남음 | 다음 집계 시작 시 1시간 이상 heartbeat가 갱신되지 않은 실행을 실패 처리 |
| 서버 중단으로 정기 배치를 놓침 | 시작 시 조건을 확인하고 어제까지의 누락 날짜 집계 |

트랜잭션의 단위는 **하루**입니다. 예를 들어 1~7일 재집계 중 4일에서 실패하면, 1~3일의 성공 결과는 유지하고 4일의 변경은 롤백합니다. 전체 기간을 한 번에 되돌리는 구조는 아닙니다.

또한 **데이터가 없어서 0인 날짜와 아직 집계되지 않은 날짜를 구분**했습니다. 집계되지 않은 기간을 정상적인 0으로 보여주거나, 일부 결과만 완전한 통계처럼 제공하지 않도록 처리했습니다.

### Read Model의 허용 범위

통계는 여러 도메인의 데이터를 읽어야 했지만, 프로젝트에는 다른 도메인의 테이블을 직접 사용하지 않는 경계 규칙이 있었습니다.

대시보드·통계·집계 배치에 한해 Read Model 조회를 허용하고, 원본을 읽는 역할과 파생 데이터를 쓰는 역할을 분리했습니다.

- **원본 조회 Mapper:** 다른 도메인의 테이블을 SELECT하고 조회 전용 DTO를 반환
- **집계 저장 Mapper:** 전달받은 값으로 통계 도메인의 집계 테이블만 변경
- **사용 범위:** 재생성 가능한 통계 데이터 생성에 사용하며, 원본 도메인의 상태 변경 판단에는 사용하지 않음

리뷰 과정에서 이 경계를 보완하고 문서에 허용 조건을 명시했습니다. 예외를 두더라도 데이터 소유권과 변경 책임이 흐려지지 않도록 고민한 경험입니다.

### 확인한 결과와 남은 한계

반복 재집계, 누락 날짜 보충, 중복 실행 제한, 실패 시 기존 결과 보존을 검증하는 테스트를 작성했습니다. 수동 재집계와 시작 시 누락 집계는 로컬 실행 결과도 PR에 기록했습니다.

화면 조회가 원본 반복 집계에서 집계 테이블 조회로 바뀌었지만, **대규모 데이터에서의 응답 시간이나 개선율은 측정하지 않았습니다.** 집계 테이블을 유지하는 비용과 데이터 갱신 지연도 함께 고려해야 합니다. 과거 변경 탐색은 원본의 변경 시각을 기준으로 하므로, 모든 변경을 무조건 자동 복구한다고 일반화하지 않습니다.

## 프로젝트를 통해 배운 점

**기술을 직접 연결하며 이해했습니다.**  
SQL 작성, Service의 업무 처리, Controller의 Model 전달, Thymeleaf 렌더링을 구현하면서 각 기술의 역할이 구체적으로 보이기 시작했습니다.

**내 도메인을 이해하려면 연결되는 도메인도 알아야 했습니다.**  
상품 기능을 완성하려면 주문·결제·장바구니가 어떤 데이터를 필요로 하는지, 실패와 중복 처리를 누가 책임질지 함께 이해해야 했습니다.

**정상 흐름을 구현한 뒤에도 설계는 계속됐습니다.**  
처음 예상한 것보다 예외 상황이 다양했습니다. 리뷰와 테스트를 통해 놓친 조건을 확인하면서, 현재 상태·작업 이력·트랜잭션 경계를 구분하는 관점을 배웠습니다.

**조회 효율을 위한 선택에는 추가 책임이 따랐습니다.**  
집계 결과를 저장하면 원본 변경 반영, 누락 감지, 재실행과 복구 방법까지 마련해야 한다는 점을 경험했습니다.
